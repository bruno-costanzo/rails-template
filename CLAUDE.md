# CharcoTemplate

Rails starter template. This repo is both a working app and the template new apps are born from (`bin/rename <new_app_name>` after cloning).

## Stack
- Ruby 4.0.6, Rails 8.1.3.1, SQLite everywhere (Solid Queue/Cache/Cable on SQLite)
- Propshaft + Importmap (no Node), Tailwind v4 + DaisyUI 5 (vendored `app/assets/tailwind/daisyui.mjs`, `app/assets/tailwind/daisyui-theme.mjs`)
- Hotwire (Turbo + Stimulus), Lexxy for Action Text rich text
- Lucide icons via `lucide-rails` (`lucide_icon` helper, inline SVG, no icon font/CDN)
- RubyLLM (OpenAI only: gpt-4o-mini / text-embedding-3-small), Schematist for structured output, Neighbor + sqlite-vec for vector search
- Native Rails authentication (+ custom registration/profile), Active Storage avatars
- console1984 for audited production console access (depends on Active Record encryption)
- money-rails for currency handling (default currency USD in `config/initializers/money.rb`, no monetized model ships — apps opt in per-model)
- letter_opener_web for development-only email preview at `/letter_opener` (development Gemfile group only)
- noticed for in-app notifications (bell UI + `/notifications`); the template ships zero notifiers — capability only
- madmin superadmin resource panel at `/madmin`, plus Mission Control (`mission_control-jobs`) Solid Queue dashboard at `/jobs` — both gated by the shared superadmin basic auth (see Superadmin panels)
- `railspress-engine` blog/CMS engine mounted at `/railspress` (admin/CMS UI at `/railspress/admin`); the reader-facing frontend is the template's own `BlogController` at `/blog` (see Blog / content)
- Bilingual UI via Rails i18n + `rails-i18n` (framework strings): Spanish default, English fallback, locale detected from the browser's `Accept-Language` header (no in-app switcher) — see Internationalization
- Minitest + fixtures + WebMock (tests NEVER hit the network), Capybara + cuprite (Ferrum/CDP driver) for system tests, bullet for N+1 detection (raises in test, logs in development), Kamal deploys

## Commands
- `bin/setup` — install and prepare everything
- `bin/dev` — run app + Tailwind watcher
- `bin/ci` — the pre-commit gate; run it before every commit, it is exactly what CI runs. It's Rails' native CI runner (`ActiveSupport::ContinuousIntegration`), configured in `config/ci.rb` with six steps: rubocop, brakeman, `i18n-tasks health`, `bin/rails test`, `bin/rails test:system`, and `bin/smoke-rename`
- `bin/rename <name>` — turn the template into a new app
- `bin/smoke-rename` — smoke test of the template's core promise: exports the tracked tree to a tmp dir, runs `bin/rename smoke_app`, asserts NO old-name references survive (outside the intentionally-skipped `docs/`), then boots the renamed copy (`db:prepare` + `zeitwerk:check`) so a leftover `CharcoTemplate` constant fails loudly. Reuses the existing bundle (rename never touches the Gemfile) so it runs in ~4s. Runs as the last `bin/ci` step. Inherits the caller's active Ruby (no `mise exec` inside, matching the other steps). `zeitwerk:check` eager-loads without decrypting credentials, so it needs no master key — `config/master.key` is copied into the copy only as a local safety belt (gitignored, absent in CI, which still boots fine). Complements the `renamer_test.rb` unit tests (which check the string rewriting in isolation) with a real end-to-end boot.

All Ruby/Rails commands run under `mise exec ruby@4.0.6 -- <command>` in non-mise-shimmed shells (e.g. `mise exec ruby@4.0.6 -- bin/rails test`).

## Conventions
- TDD always: failing test first, minimal implementation second.
- Code, comments, and identifiers stay English. User-facing copy is NEVER hardcoded — it goes through i18n (`t(...)`), lives in `config/locales/{es,en}.yml` (Spanish default, English fallback), and is enforced by `i18n-tasks health` in CI and `raise_on_missing_translations` in test (see Internationalization). No code comments. No inline styles.
- DaisyUI component classes before custom CSS.
- Controllers scope data through `Current.user` (see `ChatsController`, `DocumentsController`).
- LLM calls in tests use `stub_openai_chat` / `stub_openai_chat_stream` / `stub_openai_chat_stream_with_tool_call` / `stub_openai_embedding` (test/test_helpers/openai_stubs.rb).
- Background work goes to Solid Queue jobs (see `GenerateDocumentEmbeddingJob`).
- 100% line and branch coverage is enforced by SimpleCov; `bin/rails test` fails below 100%. Write the test first; never delete a failing coverage gate. System tests run with `SKIP_COVERAGE=1` and are excluded from measurement. `simplecov-console` (test-group gem, wired in `test/test_helper.rb` via a `MultiFormatter` alongside the HTML formatter) prints a terminal table on every run: when coverage drops it lists each sub-100% file with the exact uncovered line numbers (`missing` column) and uncovered branches — no need to open the HTML report. Coverage exclusions use `skip` (not the deprecated `add_filter`).
- N+1 queries fail tests: `Bullet.raise = true` in `config/environments/test.rb` turns any detected N+1 into a test failure (strict mode, applies to unit/controller/integration/system tests alike, see README's "N+1 detection"). Fix real N+1s with `includes`/`preload`/counter cache; only safelist a verified false positive, as narrowly as possible, with the reasoning recorded.
- Commits: short imperative messages, no co-author trailers.

## Subsystem map
- Auth: `app/controllers/concerns/authentication.rb`, `SessionsController`, `RegistrationsController`, `ProfilesController`. Avatars via Active Storage variants (`User#avatar`, `thumb`/`medium`) with an initials fallback (`User#initials`). No 2FA out of the box — see README's "Adding 2FA later" for the rotp path. **Email confirmation on signup (block-until-confirmed default):** new users are created UNCONFIRMED (`users.confirmed_at` nil); `RegistrationsController#create` no longer auto-signs-in — it `EmailConfirmationsMailer.confirm(user).deliver_later` and redirects to sign-in with a "check your email" notice, and `SessionsController#create` blocks login until confirmed (`if user.confirmed?` … else `sessions.create.unconfirmed`). The link is `GET /email_confirmations/:token` → `EmailConfirmationsController#show` (resolves the token, `User#confirm!`, redirects to sign-in; invalid/expired → resend form); resend is `GET /email_confirmations/new` + `POST /email_confirmations` (`create`, rate-limited 10/3.min, only mails an existing still-unconfirmed address but always redirects with the same notice so it never leaks whether an email exists). Token is `User.generates_token_for :email_confirmation, expires_in: 1.day do email_address end` (tied to the email, self-invalidating on change); `User#confirmed?`/`#confirm!` (idempotent) on the model; the `users` fixtures set `confirmed_at` so existing sign-in tests keep working. To relax to "allow sign-in but mark unconfirmed", change the `user.confirmed?` guard in `SessionsController#create`. Copy is i18n'd (`email_confirmations.*`, `email_confirmations_mailer.confirm.*`, `sessions.create.unconfirmed`). **Self-service account deletion (right to erasure):** the profile page (`app/views/profiles/edit.html.erb`) ends in a "Danger zone" card that posts `DELETE /registration` to `RegistrationsController#destroy` (route `resource :registration, only: %i[new create destroy]`; `destroy` is NOT in `allow_unauthenticated_access`, so it needs a signed-in user). Deletion is double-gated — both a hard-to-do-by-accident confirmation AND identity proof: the user must type the EXACT locale phrase `t("registrations.destroy.confirmation_phrase")` ("QUIERO BORRAR MI CUENTA" / "I WANT TO DELETE MY ACCOUNT", shown verbatim in the view) checked as `params[:confirmation].to_s.strip == …` AND pass `Current.user.authenticate(params[:password])`; a wrong phrase OR wrong password redirects back to `edit_profile_path` with `registrations.destroy.error` and deletes nothing. On success it's `Current.user.destroy` (true erasure, not soft-delete — cascades sessions/chats/documents/feedbacks/notifications via `User`'s existing `dependent: :destroy`, avatar purged) then `terminate_session` and redirect to sign-in with `registrations.destroy.notice`. Copy is i18n'd (`registrations.destroy.*`, `profiles.edit.danger_zone`/`delete_warning`/`confirmation_*`/`password_label`/`delete_account`); covered by four controller tests (happy path asserting the chat cascade, wrong phrase, wrong password, requires-auth). Nuance: `User`'s `dependent: :destroy` does NOT reach RailsPress author records — an app that enables RailsPress authors should decide whether a deleted user's posts nullify or destroy (a no-op by default, since authors are off).
- Data export (right to portability, the pair of the deletion above): a signed-in user requests a full export of their data from the same profile "Your data" card. It's ASYNC — `POST /data_export` (`DataExportsController#create`) enqueues `DataExportJob.perform_later(Current.user)` and redirects with a "we'll email you" notice; the job builds a ZIP via `DataExport` (`app/models/data_export.rb`), attaches it to `User#data_export` (`has_one_attached`, no migration — reuses Active Storage), and `DataExportMailer.ready(user).deliver_later` mails a link to `GET /data_export` (`#show`), which requires a signed-in session and streams `Current.user.data_export` (or a "not ready yet" notice) — the email carries the auth-gated app URL, NOT a bare signed blob URL, because a ZIP of someone's whole account can't hang off a leakable link. **The export is automatic + exception-based (Bruno's call): DRY over explicit allowlists.** `DataExport#exported_associations` walks `User.reflect_on_all_associations` for `dependent: :destroy` (the SAME set the account-deletion cascade erases — "what's erased" = "what's exported"), minus framework-internal ones (`domain_association?` drops `ActiveStorage::`/`ActionText::` reflections, since `has_one_attached`/`has_rich_text` also declare `dependent: :destroy` associations). Each record is `as_json(except: EXCLUDED_COLUMNS[class])`; the shipped exceptions are the security-critical defaults — `User => password_digest` (a password hash must never leave the app, even to its owner) and `Document => embedding` (a 1536-float vector, noise to a human). Attachments are pulled generically via `ActiveStorage::Attachment.where(record:).where.not(name: EXCLUDED_ATTACHMENTS)` into `files/<assoc>/<id>/<name>/<filename>` (excluding `data_export` itself so exports don't nest). Adding a model with `dependent: :destroy` on `User` auto-includes it in BOTH deletion and export — extend `EXCLUDED_COLUMNS`/`EXCLUDED_ATTACHMENTS` to trim. **Encryption caveat (important once an app uses `encrypts`):** Active Record Encryption decrypts transparently on read, and `as_json` reads through it, so an `encrypts`'d column is exported as PLAINTEXT — correct for portability (the person gets readable data), but it means (a) genuinely-secret encrypted fields (tokens, an `otp_secret`, API keys) must be added to `EXCLUDED_COLUMNS` exactly like `password_digest`, and (b) the generated ZIP is decrypted-at-rest, so it must not linger. A test in `data_export_test.rb` pins this (an `encrypts`'d probe column comes out decrypted, and is removed when excluded — it configures explicit keys so it runs in CI, which has no master key). The template ships zero `encrypts` on domain models today, so nothing sensitive is decrypted yet. **Lifecycle (the answer to "don't leave decrypted data around"):** `DataExport::RETENTION = 48.hours`; `DataExportsController#show` refuses to serve an export past that window (purges it, shows `data_exports.show.expired`), and a `purge_expired_data_exports` recurring task (`config/recurring.yml`, `command: "DataExport.purge_expired"`) sweeps expired export attachments hourly in production. **Action Text rich text IS exported:** `serialize` detects `has_rich_text` associations generically (reflections with `class_name: "ActionText::RichText"`) and adds each one's `to_plain_text` under the attribute name (e.g. `Document#content`); `records_for` eager-loads those rich-text associations (`.includes(...)`) so walking many records doesn't trip Bullet. `to_plain_text` (not `to_html`) is deliberate — it never renders attachment partials, so it's safe in the job context with no view/URL dependencies. Remaining limitation: rich-text formatting and EMBEDDED files (images attached to the `ActionText::RichText` record, not the owner) aren't included — only the text. Fully i18n'd (`data_exports.*`, `data_export_mailer.ready.*`, `profiles.edit.export_*`), 100% covered (model/job/mailer/controller tests). Note: request locale is scoped per-request via `ApplicationController#switch_locale` (`around_action` + `I18n.with_locale`, NOT a bare `I18n.locale =` assignment) precisely so the global locale never leaks across requests/parallel tests.
- Email: production ships an ACTIVE, provider-agnostic SMTP scaffold in `config/environments/production.rb` (`delivery_method = :smtp`; `smtp_settings` reads `Rails.application.credentials.dig(:smtp, :user_name)`/`:password` first, then `ENV["SMTP_USER_NAME"]`/`ENV["SMTP_PASSWORD"]`, `address: ENV["SMTP_ADDRESS"]`, `port: ENV.fetch("SMTP_PORT", 587)`, `authentication: :plain`, `enable_starttls_auto: true`) plus `default_url_options = { host: ENV.fetch("APP_HOST", "example.com"), protocol: "https" }`. The wiring is in the template (works with any provider — SendGrid/Postmark/Mailgun/SES/Resend/…); each app fills only the secrets (`APP_HOST` + `SMTP_*` or the `smtp/*` credentials block), documented in `.env.example`. `APP_HOST` must be set before deploying or mailer links fall back to `example.com`. Dev previews mail via letter_opener_web at `/letter_opener`; test uses the `:test` delivery method. See README's "Configuration".
- AI chat: RubyLLM `acts_as_chat`-generated models (`Chat`, `Message`, `ToolCall`, `Model`), scoped per user through `Current.user`. `ChatResponseJob` streams the assistant response and, only after it persists, enqueues `GenerateChatTitleJob` (event-driven, race-safe — it never runs before the first message exists). Titling uses `RubyLLM.chat.with_schema(ChatTitleSchema)` (`app/schemas/chat_title_schema.rb`, a Schematist schema). `Message#to_partial_path`/`#hidden_from_person?` build a full `to_llm` representation per message (touching `tool_calls`, `parent_tool_call`, `model`, and `attachments`), so both `ChatsController#show` and `SupportChatsController#show` set `@messages` with `.includes(:tool_calls, :parent_tool_call, :model, attachments_attachments: :blob)` to avoid a Bullet-caught N+1 once a chat has more than one message.
- Semantic search: `Document` (`semantic_search`, `EMBEDDING_DIMENSIONS = 1536`) enqueues `GenerateDocumentEmbeddingJob` from an `after_save_commit` callback guarded by `saved_change_to_embedding?` (avoids re-embedding loops), `config/initializers/neighbor.rb` calling `Neighbor::SQLite.initialize!` (sqlite-vec extension).
- Rich text: Action Text + Lexxy (`import "lexxy"` in `app/javascript/application.js`, manual `pin "lexxy"` in `config/importmap.rb`, `stylesheet_link_tag "lexxy"` in the layout). On Rails 8.1, Lexxy falls back to monkey-patching `rich_text_area`/`rich_textarea` instead of using the official `ActionText::Editor` adapter API (merged later in Rails). Re-verify `Lexxy.supports_editor_adapter?` after any Rails upgrade — the rendered `<lexxy-editor>` tag should stay the same either way, but re-run the Lexxy system test to confirm.
- Console auditing: console1984 records production console sessions/commands and requires Active Record encryption (keys live in `config/credentials.yml.enc`, generated via `bin/rails db:encryption:init`). See README's Console auditing and Quickstart sections — new apps must regenerate their own credentials, since `config/master.key` never travels with the repo.
- Superadmin panels: every developer-only panel is gated by ONE shared HTTP basic-auth credential pair through the `SuperadminAuthentication` concern (`app/controllers/concerns/superadmin_authentication.rb`), independent of session auth. Credentials resolve credentials-first then ENV, live on every request: `Rails.application.credentials.dig(:superadmin, :username)`/`:password`, falling back to `ENV["SUPERADMIN_USER"]`/`ENV["SUPERADMIN_PASSWORD"]`; comparison via `ActiveSupport::SecurityUtils.secure_compare`. **Deny-by-default**: when either is blank every request gets a `401` (`request_http_basic_authentication("Superadmin")`) — there is no "open when unconfigured" fallback anywhere (stricter than the Solid Errors / onlylogs gem defaults). The concern's `included do … end` registers `before_action :authenticate_superadmin!`, so a controller only needs `include SuperadminAuthentication`. Five panels use it: `/errors` (via `SolidErrors.base_controller_class = "SolidErrorsBaseController"`), `/onlylogs` (via `OnlylogsBaseController`), `/admin/feedbacks` (`Admin::FeedbacksController`, still `allow_unauthenticated_access` for session auth), `/jobs` (Mission Control — Solid Queue dashboard, via `MissionControl::Jobs.base_controller_class = "MissionControlJobsBaseController"` with `MissionControl::Jobs.http_basic_auth_enabled = false` in `config/initializers/mission_control_jobs.rb` so the gem's own basic auth no-ops and only the superadmin concern gates it), and `/madmin`. `/madmin` is the madmin (~2.6) resource panel: `Madmin::ApplicationController` (`app/controllers/madmin/application_controller.rb`) includes the concern and adds `around_action :without_bullet if defined?(Bullet)` (madmin's generated index views lazy-load associations, which would otherwise trip the strict Bullet N+1 gate — acceptable for a dev-only panel over bounded data). Dashboards exist only for domain models — `Chat`, `Document`, `Feedback`, `Message`, `Model`, `Session`, `ToolCall`, `User`, plus `Noticed::Notification`/`Noticed::Event`; the framework-internal/sensitive resources the generator created (ActiveStorage, ActionText, console1984 audit logs, Solid Errors — already at `/errors`) were pruned from `config/routes/madmin.rb`, `app/madmin/resources/`, and `app/controllers/madmin/`. madmin files are excluded from coverage via `skip "app/madmin"`/`skip "app/controllers/madmin"` in `test/test_helper.rb`. Add a new model's dashboard with `bin/rails g madmin:resource ModelName` **after** its migration has run (then prune/route as above) — the generator reads the model's columns via `attribute_names`/`attribute_types`, so the table must exist. There is deliberately no auto-generation hook: `config.generators.after_generate` fires right after `rails g model`, before `db:migrate`, so a hook that ran `madmin:resource` there would fail on the not-yet-created table (this is also why madmin ships no such feature). Keep the manual `model → migrate → madmin:resource` order. A sixth consumer, the RailsPress blog admin at `/railspress/admin`, also `include`s the concern (via `RailspressAdminAuth`), but that superadmin gating is a **temporary placeholder**: conceptually the blog admin is an app content-editor panel (a system user with a content role), not a developer panel — see Blog / content for the swap seam. See README's "Superadmin access".
- Error tracking: Solid Errors subscribes to `Rails.error` (`config/initializers/solid_errors.rb`) and persists deduplicated exceptions to the primary DB (`solid_errors`/`solid_errors_occurrences`, migrated normally — no separate database). Dashboard mounted at `/errors` (`config/routes.rb`), gated by the shared superadmin basic auth (see Superadmin panels): `config/initializers/solid_errors.rb` sets `SolidErrors.base_controller_class = "SolidErrorsBaseController"` (which just `include SuperadminAuthentication`, so `/errors` is deny-by-default and never open — the initializer no longer sets `SolidErrors.username`/`password`, leaving the gem's own `http_basic_authenticate_with ... if SolidErrors.password` inert). Only email stays panel-specific: `email_to`/`email_from`/`send_emails` resolve from `Rails.application.credentials.dig(:solid_errors, :email_to)` then `ENV["SOLID_ERRORS_EMAIL_TO"]`, and notification only fires when `email_to` resolves. See README's Error tracking section.
- User feedback: `Feedback` (`belongs_to :user`, `has_many_attached :photos`, content_type/size-validated like `User#avatar`) always persists locally via `FeedbacksController#create` (`/feedback`, linked from the navbar dropdown). `after_create_commit` enqueues `CreateFeedbackIssueJob`, which no-ops unless `GithubIssues.configured?` (both `GITHUB_ISSUES_TOKEN` and `GITHUB_ISSUES_REPO` set) and otherwise POSTs a labeled (`feedback`) issue to `https://api.github.com/repos/#{repo}/issues` via `GithubIssues` (`app/models/github_issues.rb`, plain `Net::HTTP`, no new gem, `X-GitHub-Api-Version: 2022-11-28`). A non-2xx response raises; the job has no custom retry config, so it relies on Solid Queue's default retry-with-backoff, and Solid Errors captures exhausted failures. Photos are linked in the issue body through the permanent public route `/feedback/photos/:signed_id` (`FeedbackPhotosController`), which only redirects to blobs actually attached to a `Feedback#photos` — never an open blob proxy. Those photo links are absolute URLs built from `config.action_mailer.default_url_options`; `production.rb` derives its host from `ENV.fetch("APP_HOST", "example.com")`, so new apps must set `APP_HOST` before deploying (same rule as the `config/deploy.yml` placeholders), or issue photo links (and every mailer link) point at `example.com`. See README's "User feedback" section.
- AI support assistant: a floating "Support" button (rendered from the layout for signed-in users, `app/views/support_chats/_widget.html.erb`) opens a chat panel backed by a per-user support `Chat` (`support: true`, found-or-created by `SupportChatsController#show`, scoped through `Current.user`). Support chats are excluded from `ChatsController#index` (`Chat.support` scope in `app/models/chat.rb`). `SupportAgent < RubyLLM::Agent` (`app/agents/support_agent.rb`) declares `chat_model "Chat"`, `instructions { SupportContext.instructions }` and `tools { [CreateSupportTicketTool.new(chat)] }` (`chat` inside that block is the runtime context's chat record, per RubyLLM's `Agent#tools` block API; the tool takes the whole chat, not just its user, so it can also reach `ticket_context` and `pending_photos`). `ChatResponseJob` calls `SupportAgent.find(chat_id)` instead of `Chat.find` only when `chat.support?`; normal chats are untouched. `Agent.find` applies configuration with `persist_instructions: false`, which RubyLLM routes to `Chat#with_runtime_instructions` — the instructions are injected into the in-memory `RubyLLM::Chat` sent to the API on every turn but are never written as a `messages` row, so repeated finds across a multi-turn conversation can never duplicate or go stale in the persisted system message (verified against `ruby_llm-1.16.0/lib/ruby_llm/agent.rb:181-193` and `.../active_record/chat_methods.rb:106-110,326-332`). **Binding rule, verbatim from the product owner: "es importante q nunca le filtre codigo a la persona, es decir, para la persona debe ser solo human friendly"** — nothing the person sees may ever contain code, file names, stack traces, class names, or other technical internals. Enforced three ways: (1) `SupportContext::BINDING_RULE` (`app/models/support_context.rb`) states the rule in the system prompt for every support chat; (2) `config/support_context.md` — the only app-specific knowledge given to the assistant — is human-friendly-only by convention (ships as a placeholder with guided sections: what the app does, common problems, what to ask for a bug report vs. a suggestion; keep it non-technical); (3) `Message#to_partial_path` (`app/models/message.rb`) renders system/tool-call/tool-result messages as a blank partial in support chats specifically, so even a leaked tool call never reaches the UI (normal chats still show them in full, for transparency). `CreateSupportTicketTool` (`app/tools/create_support_ticket_tool.rb`, a `RubyLLM::Tool`) files the refined ticket as a `Feedback` for the chat's user, reusing Task 22's `after_create_commit → CreateFeedbackIssueJob` pipeline untouched — the ticket itself can be as technical as needed, since it's for the developer, not the person. Needs `OPENAI_API_KEY` to reply at all; GitHub forwarding is independently optional as in "User feedback" above.
  - Ticket context and photos (Task 26): the widget's Stimulus controller (`support_chat_controller.js`) captures `page_url`/`user_agent`/`viewport` on first open and appends them as `context[...]` query params on the frame's request to `SupportChatsController#show`, which whitelists those three keys and truncates each to 2 kilobytes before storing them as plain, never-interpreted text in `Chat#ticket_context`. That column is **not** named `context` — RubyLLM's `acts_as_chat` (`ChatMethods`) already defines its own `attr_accessor :context` for provider request configuration, and a same-named DB column silently collides with it (`chat.context` reads back the RubyLLM object, and any write blows up `resolve_model_from_strings`'s `context&.config` call on the next save — reproduced against `ruby_llm-1.16.0/lib/ruby_llm/active_record/chat_methods.rb:15,47`). `Feedback#context` has no such conflict (plain `ApplicationRecord`) and is the copy target: `CreateSupportTicketTool#execute` copies `chat.ticket_context` there, and `CreateFeedbackIssueJob` renders it as a `Context:` block inside the trusted, developer-only metadata section before the `---` separator. The widget's attach control (`lucide_icon("paperclip")`) uploads immediately to `POST /support_chat/photos` (`SupportChatPhotosController`, scoped through `Current.user.chats.find_by!(support: true)` — no cross-user attachment possible) onto `Chat#pending_photos` (`has_many_attached`, validated identically to `Feedback#photos`). On ticket filing, the tool attaches those same blobs onto `Feedback#photos` and calls `chat.pending_photos.detach` — deliberately not `.purge`. `Blob#purge` (`blob.rb:335-339`) does `rescue ActiveRecord::InvalidForeignKey`, and the `active_storage_attachments → active_storage_blobs` FK in this app's schema (SQLite FKs on by default) would in practice stop it from deleting a blob the `Feedback` still references — but depending on that rescue for correctness is fragile (FK presence/enforcement is an environment detail, not a guarantee). `.detach` avoids depending on that rescue entirely: it only removes the join row and never touches the blob (verified against `activestorage-8.1.3.1/lib/active_storage/attached/many.rb:8-27` and the `attachment.rb:6-9` class doc, which states the FK "prevents blobs from being purged if they're still attached to any records").
- Ticket lifecycle: `Feedback` (Task 22) has a `status` enum (`open`/`resolved`, default `open`) and `resolved_at`. `Feedback#resolve!` sets both and is idempotent — a no-op (doesn't touch `resolved_at`, doesn't raise) when already resolved. `Admin::FeedbacksController` (`/admin/feedbacks`) lists `Feedback.open` (the enum's auto-generated scope) with a `resolve` member action; the view reuses the public `/feedback/photos/:signed_id` route for photo links, same as `CreateFeedbackIssueJob`'s issue body. No notification of any kind fires on resolution — this panel is ticket control only. `Admin::FeedbacksController` `include SuperadminAuthentication` (see Superadmin panels) for its HTTP basic auth — the shared `SUPERADMIN_USER`/`SUPERADMIN_PASSWORD` (or `credentials.dig(:superadmin, …)`), resolved live per request, deny-by-default (always `401` when unconfigured); it keeps `allow_unauthenticated_access` so the app's session auth is skipped and only the superadmin gate applies. - Log viewer: onlylogs 0.7 mounted at `/onlylogs` (`config/routes.rb`, next to Solid Errors). Production logs broadcast (`ActiveSupport::BroadcastLogger` in `config/environments/production.rb`) to STDOUT (Kamal capture unchanged) AND `storage/logs/production.log`, rotated by Ruby's `Logger` (`5, 100.megabytes` → at most `production.log` + `.0`–`.3`, ~500 MB hard cap on the storage volume). `config/initializers/onlylogs.rb` whitelists exactly that path via `config.log_file_patterns` (the gem auto-permits `.log.N` rotation suffixes and lists them in the viewer; `log/<env>.log` is added outside production so the viewer works locally) and bypasses the gem's built-in basic auth (403-when-unconfigured, ENV-before-credentials, read once at Configuration.new) with its documented custom-auth hook: `config.disable_basic_authentication = true` + `config.parent_controller = "OnlylogsBaseController"`. That controller (`app/controllers/onlylogs_base_controller.rb`) just `include SuperadminAuthentication` (see Superadmin panels), so `/onlylogs` is gated by the shared `SUPERADMIN_USER`/`SUPERADMIN_PASSWORD` (deny-by-default, live per request, secure_compare) — the gem's own `authenticate_onlylogs_user!` no-ops under `disable_basic_authentication` and the concern's `before_action` does the work. **Basic auth covers the HTTP surface only**: the live tail runs over Action Cable and `Onlylogs::LogsChannel` never checks onlylogs credentials — its boundary is the app's cable connection (any signed-in user; the template ships open self-registration) plus whitelist + `SecureFilePath` encryption. The gem's blank-`file_path` fallback streams `default_log_file_path` with NO decryption/whitelist check (`logs_channel.rb:31-34` in onlylogs 0.7.0), so the initializer deliberately sets `config.default_log_file_path = ""` (a never-existing path the channel's text-file check rejects); never point it at a real log — `test/channels/onlylogs_logs_channel_test.rb` guards this. Residual risk: a signed-in user holding a valid encrypted path token (non-expiring, secret_key_base-keyed, normally rendered only behind `/onlylogs` basic auth) can still stream that whitelisted file over the socket. Upstream gap to patch in renuo/onlylogs: no parent_controller-equivalent hook for the channel. - Internationalization: the UI is bilingual (Spanish + English) with **Spanish as the default locale and English as the fallback** — `config/application.rb` sets `config.i18n.available_locales = [:es, :en]`, `default_locale = :es`, `fallbacks = [:en]`; `rails-i18n` supplies framework strings (dates, numbers, Active Record error messages). Locale is chosen per request from the browser's `Accept-Language` header in `ApplicationController#set_locale`/`#locale_from_accept_language` (picks the first 2-letter subtag in `available_locales`, else `:es`) — there is **no in-app language switcher and it is not user-configurable by design**: a visitor gets English only if their browser prefers it, otherwise Spanish. **No user-facing copy is hardcoded**: everything is `t(...)` against `config/locales/es.yml` + `config/locales/en.yml` (~127 keys, en/es fully in sync). Convention: views use lazy lookups `t(".key")` (resolve to `<controller>.<action>.key`); shared partials/layouts use explicit `shared.*`/`layouts.*` keys; controllers translate flash; mailers translate subject and body. Two enforcement gates, in the same spirit as the coverage/Bullet gates: `config.i18n.raise_on_missing_translations = true` in `config/environments/test.rb` (a `t()` on a missing key raises during the suite), and an `i18n-tasks health` step in `config/ci.rb` (`config/i18n-tasks.yml`, `base_locale: es`; the `i18n-tasks` gem is in the development/test group with a `bin/i18n-tasks` binstub) that fails CI on missing/unused keys or inconsistent interpolations. There is deliberately **no static "hardcoded string in ERB" cop** — no robust tool exists (rubocop-i18n only sees the Ruby inside `<%= %>`, not literal HTML, and floods false positives), so the two gates plus review are the enforcement. To add copy: wrap it in `t(".key")`, add the key to BOTH `es.yml` and `en.yml`, then `bin/i18n-tasks normalize` (and `bin/i18n-tasks health` to verify). Tests assert against `I18n.t(key)`/locale-aware matchers, never English literals, so they are locale-independent; the **system tests run in English** because headless Chrome sends `Accept-Language: en-US` (the Spanish default path is covered by the unit/integration suites, which send no header, and by `test/integration/locale_detection_test.rb`). See README's "Internationalization" section.
- Blog / content (RailsPress): `railspress-engine` (~1.4) mounted at `/railspress` (`config/routes.rb`) is the authoring/CMS back-office — draft/publish/schedule posts (Lexxy rich text), categories, tags, optional authors, auto-slugs, per-post SEO (`meta_title`/`meta_description`), header images/galleries, plus Entities (custom models) and CMS Blocks, and a JSON API — all behind its admin UI at `/railspress/admin`. It ships **no public reader pages** (the engine's routes are `admin` + `api` only), so the template provides its own frontend: `BlogController` (`app/controllers/blog_controller.rb`, `allow_unauthenticated_access`) serves `/blog` (`blog#index`) and `/blog/:id` (`blog#show`, lookup by slug). Index lists `Railspress::Post.published` newest-first with optional `?category=<slug>`/`?tag=<slug>` filters, eager-loading `includes(:category, :tags).with_attached_header_image` to satisfy the strict Bullet gate; show renders the post's Action Text `content` and sets SEO via the `meta-tags` gem (`meta_title`/`meta_description`, falling back to the title and a truncated plain-text content); a draft or unknown slug is `404`. Views are DaisyUI (`app/views/blog/`), copy is i18n'd (`blog.*` keys in `config/locales/{es,en}.yml`) — RailsPress owns the back-office, the public presentation is the template's and you restyle it per app. **Admin authorization is the one seam to change per app.** `/railspress/admin` is gated by the shared superadmin basic auth *only as a safe default* — `config/initializers/railspress.rb` sets `config.admin_auth_concern = "RailspressAdminAuth"`, and `app/controllers/concerns/railspress_admin_auth.rb` just `include SuperadminAuthentication`. But the blog admin is meant for an APP content-editor (a system user with a content role), not the dev superadmin; the template ships superadmin gating only because it has no content-editor role yet (authorization is capability-only, per-app) and open self-registration makes gating by bare `authenticated?` unsafe. To re-gate per app, edit that single concern — e.g. from `include SuperadminAuthentication` to a before_action that authorizes a content-editor: `included { before_action :require_content_editor }` + `def require_content_editor; redirect_to(main_app.root_path, alert: "…") unless Current.user&.content_editor?; end`. Two notes: a narrow Bullet safelist in `config/environments/test.rb` covers `Railspress::Post => :taggings` unused-eager-loading (a verified `has_many :through` false positive — the join is loaded to serve `.tags` but never touched directly); and `superadmin_authentication.rb` + `railspress_admin_auth.rb` are excluded from SimpleCov (`skip` in `test/test_helper.rb`) because the RailsPress engine's `config.to_prepare` includes them into its admin controller at BOOT and Ruby's Coverage under parallel workers can't attribute boot-loaded lines — their behavior is still verified functionally by the five panels' integration tests (401 unconfigured / 200 with creds / deny-by-default), mirroring the madmin coverage exclusion. Gotcha: RailsPress 1.4.4 declares a `railspress_fields :excerpt` but ships no `excerpt` column, so `Railspress::Post#excerpt` does not exist — don't use it. See README's "Blog & content".

- Security headers / CSP: a nonce-based Content Security Policy is ACTIVE (`config/initializers/content_security_policy.rb`, all environments — previously the initializer was fully commented). Policy: `default-src`/`base-uri`/`form-action`/`frame-ancestors 'self'` (clickjacking-safe), `object-src 'none'`, `font-src 'self' data:`, `img-src 'self' data: blob: https:` (permissive for user/blog content + Active Storage), `connect-src 'self'` (covers the same-origin Action Cable WebSocket behind Turbo Streams/streaming), `style-src 'self' 'unsafe-inline'`, and `script-src 'self'` + a per-request nonce. **Scripts strict, styles unsafe-inline** — scripts are the real XSS vector so `script-src` is nonce-based (`content_security_policy_nonce_generator = ->(request) { SecureRandom.base64(16) }`, `content_security_policy_nonce_directives = %w[script-src]`; `SecureRandom` rather than Rails' default `request.session.id` so public/session-less pages like sign-in and `/blog` still get a nonce without a session being created for it), and `javascript_importmap_tags` + the layout's `csp_meta_tag` propagate the nonce so importmap/Turbo/Stimulus keep working; styles allow `'unsafe-inline'` because Lexxy and Turbo inject inline styles at runtime that can't carry a nonce (a much weaker vector). Validated by the full cuprite system suite (a broken CSP would stop importmap/Turbo/Stimulus and fail those tests) plus a guard test `test/integration/content_security_policy_test.rb` (asserts the header and `script-src 'self' 'nonce-…'`). **Caveat:** the middleware applies the CSP globally, so it also covers the mounted engine UIs (`/madmin`, `/railspress/admin`, `/jobs`, `/errors`, `/onlylogs`) — those sit behind the superadmin gate (trusted, lower risk) and are NOT system-tested under it; if a panel's JS breaks under the CSP, relax the policy for that path (or add nonces). See README's "Security headers".
