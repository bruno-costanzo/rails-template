# CharcoTemplate

Rails starter template. This repo is both a working app and the template new apps are born from (`bin/rename <new_app_name>` after cloning).

## Stack
- Ruby 4.0.6, Rails 8.1.3.1, SQLite everywhere (Solid Queue/Cache/Cable on SQLite)
- Propshaft + Importmap (no Node), Tailwind v4 + DaisyUI 5 (vendored `app/assets/tailwind/daisyui.mjs`, `app/assets/tailwind/daisyui-theme.mjs`)
- Hotwire (Turbo + Stimulus), Lexxy for Action Text rich text
- Lucide icons via `lucide-rails` (`lucide_icon` helper, inline SVG, no icon font/CDN)
- RubyLLM (OpenAI only: gpt-4o-mini / text-embedding-3-small), Schematist for structured output, Neighbor + sqlite-vec for vector search
- Native Rails authentication (+ custom registration/profile), Active Storage avatars
- console1984 for audited production console access (depends on Active Record encryption)
- money-rails for currency handling (default currency USD in `config/initializers/money.rb`, no monetized model ships — apps opt in per-model)
- letter_opener_web for development-only email preview at `/letter_opener` (development Gemfile group only)
- noticed for in-app notifications (bell UI + `/notifications`); the template ships zero notifiers — capability only
- Minitest + fixtures + WebMock (tests NEVER hit the network), Capybara + cuprite (Ferrum/CDP driver) for system tests, bullet for N+1 detection (raises in test, logs in development), Kamal deploys

## Commands
- `bin/setup` — install and prepare everything
- `bin/dev` — run app + Tailwind watcher
- `bin/ci` — the pre-commit gate; run it before every commit, it is exactly what CI runs. It's Rails' native CI runner (`ActiveSupport::ContinuousIntegration`), configured in `config/ci.rb` with four steps: rubocop, brakeman, `bin/rails test`, `bin/rails test:system`
- `bin/rename <name>` — turn the template into a new app

All Ruby/Rails commands run under `mise exec ruby@4.0.6 -- <command>` in non-mise-shimmed shells (e.g. `mise exec ruby@4.0.6 -- bin/rails test`).

## Conventions
- TDD always: failing test first, minimal implementation second.
- English-only code and copy. No code comments. No inline styles.
- DaisyUI component classes before custom CSS.
- Controllers scope data through `Current.user` (see `ChatsController`, `DocumentsController`).
- LLM calls in tests use `stub_openai_chat` / `stub_openai_chat_stream` / `stub_openai_chat_stream_with_tool_call` / `stub_openai_embedding` (test/test_helpers/openai_stubs.rb).
- Background work goes to Solid Queue jobs (see `GenerateDocumentEmbeddingJob`).
- 100% line and branch coverage is enforced by SimpleCov; `bin/rails test` fails below 100%. Write the test first; never delete a failing coverage gate. System tests run with `SKIP_COVERAGE=1` and are excluded from measurement.
- N+1 queries fail tests: `Bullet.raise = true` in `config/environments/test.rb` turns any detected N+1 into a test failure (strict mode, applies to unit/controller/integration/system tests alike, see README's "N+1 detection"). Fix real N+1s with `includes`/`preload`/counter cache; only safelist a verified false positive, as narrowly as possible, with the reasoning recorded.
- Commits: short imperative messages, no co-author trailers.

## Subsystem map
- Auth: `app/controllers/concerns/authentication.rb`, `SessionsController`, `RegistrationsController`, `ProfilesController`. Avatars via Active Storage variants (`User#avatar`, `thumb`/`medium`) with an initials fallback (`User#initials`). No 2FA out of the box — see README's "Adding 2FA later" for the rotp path.
- AI chat: RubyLLM `acts_as_chat`-generated models (`Chat`, `Message`, `ToolCall`, `Model`), scoped per user through `Current.user`. `ChatResponseJob` streams the assistant response and, only after it persists, enqueues `GenerateChatTitleJob` (event-driven, race-safe — it never runs before the first message exists). Titling uses `RubyLLM.chat.with_schema(ChatTitleSchema)` (`app/schemas/chat_title_schema.rb`, a Schematist schema). `Message#to_partial_path`/`#hidden_from_person?` build a full `to_llm` representation per message (touching `tool_calls`, `parent_tool_call`, `model`, and `attachments`), so both `ChatsController#show` and `SupportChatsController#show` set `@messages` with `.includes(:tool_calls, :parent_tool_call, :model, attachments_attachments: :blob)` to avoid a Bullet-caught N+1 once a chat has more than one message.
- Semantic search: `Document` (`semantic_search`, `EMBEDDING_DIMENSIONS = 1536`) enqueues `GenerateDocumentEmbeddingJob` from an `after_save_commit` callback guarded by `saved_change_to_embedding?` (avoids re-embedding loops), `config/initializers/neighbor.rb` calling `Neighbor::SQLite.initialize!` (sqlite-vec extension).
- Rich text: Action Text + Lexxy (`import "lexxy"` in `app/javascript/application.js`, manual `pin "lexxy"` in `config/importmap.rb`, `stylesheet_link_tag "lexxy"` in the layout). On Rails 8.1, Lexxy falls back to monkey-patching `rich_text_area`/`rich_textarea` instead of using the official `ActionText::Editor` adapter API (merged later in Rails). Re-verify `Lexxy.supports_editor_adapter?` after any Rails upgrade — the rendered `<lexxy-editor>` tag should stay the same either way, but re-run the Lexxy system test to confirm.
- Console auditing: console1984 records production console sessions/commands and requires Active Record encryption (keys live in `config/credentials.yml.enc`, generated via `bin/rails db:encryption:init`). See README's Console auditing and Quickstart sections — new apps must regenerate their own credentials, since `config/master.key` never travels with the repo.
- Error tracking: Solid Errors subscribes to `Rails.error` (`config/initializers/solid_errors.rb`) and persists deduplicated exceptions to the primary DB (`solid_errors`/`solid_errors_occurrences`, migrated normally — no separate database). Dashboard mounted at `/errors` (`config/routes.rb`), protected by HTTP basic auth independent of session auth: username/password/`email_to` resolve from `Rails.application.credentials.dig(:solid_errors, ...)` first, `ENV["SOLID_ERRORS_USERNAME"]`/`PASSWORD`/`EMAIL_TO` second. Auth is gated on password alone (`http_basic_authenticate_with ... if SolidErrors.password`) — a username with no password leaves `/errors` open, so set both before production. The gem also checks its own `ENV["SOLIDERRORS_USERNAME"]`/`PASSWORD` (no underscore between "SOLID" and "ERRORS") ahead of everything this app configures — avoid setting those exact names unless you want them to win silently. Email notification only fires when `email_to` resolves. See README's Error tracking section.
- User feedback: `Feedback` (`belongs_to :user`, `has_many_attached :photos`, content_type/size-validated like `User#avatar`) always persists locally via `FeedbacksController#create` (`/feedback`, linked from the navbar dropdown). `after_create_commit` enqueues `CreateFeedbackIssueJob`, which no-ops unless `GithubIssues.configured?` (both `GITHUB_ISSUES_TOKEN` and `GITHUB_ISSUES_REPO` set) and otherwise POSTs a labeled (`feedback`) issue to `https://api.github.com/repos/#{repo}/issues` via `GithubIssues` (`app/models/github_issues.rb`, plain `Net::HTTP`, no new gem, `X-GitHub-Api-Version: 2022-11-28`). A non-2xx response raises; the job has no custom retry config, so it relies on Solid Queue's default retry-with-backoff, and Solid Errors captures exhausted failures. Photos are linked in the issue body through the permanent public route `/feedback/photos/:signed_id` (`FeedbackPhotosController`), which only redirects to blobs actually attached to a `Feedback#photos` — never an open blob proxy. Those photo links are absolute URLs built from `config.action_mailer.default_url_options`; `production.rb` ships that as the `example.com` placeholder, so new apps must replace it with their real host before deploying (same rule as the `config/deploy.yml` placeholders), or issue photo links will point at `example.com`. See README's "User feedback" section.
- AI support assistant: a floating "Support" button (rendered from the layout for signed-in users, `app/views/support_chats/_widget.html.erb`) opens a chat panel backed by a per-user support `Chat` (`support: true`, found-or-created by `SupportChatsController#show`, scoped through `Current.user`). Support chats are excluded from `ChatsController#index` (`Chat.support` scope in `app/models/chat.rb`). `SupportAgent < RubyLLM::Agent` (`app/agents/support_agent.rb`) declares `chat_model "Chat"`, `instructions { SupportContext.instructions }` and `tools { [CreateSupportTicketTool.new(chat)] }` (`chat` inside that block is the runtime context's chat record, per RubyLLM's `Agent#tools` block API; the tool takes the whole chat, not just its user, so it can also reach `ticket_context` and `pending_photos`). `ChatResponseJob` calls `SupportAgent.find(chat_id)` instead of `Chat.find` only when `chat.support?`; normal chats are untouched. `Agent.find` applies configuration with `persist_instructions: false`, which RubyLLM routes to `Chat#with_runtime_instructions` — the instructions are injected into the in-memory `RubyLLM::Chat` sent to the API on every turn but are never written as a `messages` row, so repeated finds across a multi-turn conversation can never duplicate or go stale in the persisted system message (verified against `ruby_llm-1.16.0/lib/ruby_llm/agent.rb:181-193` and `.../active_record/chat_methods.rb:106-110,326-332`). **Binding rule, verbatim from the product owner: "es importante q nunca le filtre codigo a la persona, es decir, para la persona debe ser solo human friendly"** — nothing the person sees may ever contain code, file names, stack traces, class names, or other technical internals. Enforced three ways: (1) `SupportContext::BINDING_RULE` (`app/models/support_context.rb`) states the rule in the system prompt for every support chat; (2) `config/support_context.md` — the only app-specific knowledge given to the assistant — is human-friendly-only by convention (ships as a placeholder with guided sections: what the app does, common problems, what to ask for a bug report vs. a suggestion; keep it non-technical); (3) `Message#to_partial_path` (`app/models/message.rb`) renders system/tool-call/tool-result messages as a blank partial in support chats specifically, so even a leaked tool call never reaches the UI (normal chats still show them in full, for transparency). `CreateSupportTicketTool` (`app/tools/create_support_ticket_tool.rb`, a `RubyLLM::Tool`) files the refined ticket as a `Feedback` for the chat's user, reusing Task 22's `after_create_commit → CreateFeedbackIssueJob` pipeline untouched — the ticket itself can be as technical as needed, since it's for the developer, not the person. Needs `OPENAI_API_KEY` to reply at all; GitHub forwarding is independently optional as in "User feedback" above.
  - Ticket context and photos (Task 26): the widget's Stimulus controller (`support_chat_controller.js`) captures `page_url`/`user_agent`/`viewport` on first open and appends them as `context[...]` query params on the frame's request to `SupportChatsController#show`, which whitelists those three keys and truncates each to 2 kilobytes before storing them as plain, never-interpreted text in `Chat#ticket_context`. That column is **not** named `context` — RubyLLM's `acts_as_chat` (`ChatMethods`) already defines its own `attr_accessor :context` for provider request configuration, and a same-named DB column silently collides with it (`chat.context` reads back the RubyLLM object, and any write blows up `resolve_model_from_strings`'s `context&.config` call on the next save — reproduced against `ruby_llm-1.16.0/lib/ruby_llm/active_record/chat_methods.rb:15,47`). `Feedback#context` has no such conflict (plain `ApplicationRecord`) and is the copy target: `CreateSupportTicketTool#execute` copies `chat.ticket_context` there, and `CreateFeedbackIssueJob` renders it as a `Context:` block inside the trusted, developer-only metadata section before the `---` separator. The widget's attach control (`lucide_icon("paperclip")`) uploads immediately to `POST /support_chat/photos` (`SupportChatPhotosController`, scoped through `Current.user.chats.find_by!(support: true)` — no cross-user attachment possible) onto `Chat#pending_photos` (`has_many_attached`, validated identically to `Feedback#photos`). On ticket filing, the tool attaches those same blobs onto `Feedback#photos` and calls `chat.pending_photos.detach` — deliberately not `.purge`. `Blob#purge` (`blob.rb:335-339`) does `rescue ActiveRecord::InvalidForeignKey`, and the `active_storage_attachments → active_storage_blobs` FK in this app's schema (SQLite FKs on by default) would in practice stop it from deleting a blob the `Feedback` still references — but depending on that rescue for correctness is fragile (FK presence/enforcement is an environment detail, not a guarantee). `.detach` avoids depending on that rescue entirely: it only removes the join row and never touches the blob (verified against `activestorage-8.1.3.1/lib/active_storage/attached/many.rb:8-27` and the `attachment.rb:6-9` class doc, which states the FK "prevents blobs from being purged if they're still attached to any records").
- Ticket lifecycle: `Feedback` (Task 22) has a `status` enum (`open`/`resolved`, default `open`) and `resolved_at`. `Feedback#resolve!` sets both and is idempotent — a no-op (doesn't touch `resolved_at`, doesn't raise) when already resolved. `Admin::FeedbacksController` (`/admin/feedbacks`) lists `Feedback.open` (the enum's auto-generated scope) with a `resolve` member action; the view reuses the public `/feedback/photos/:signed_id` route for photo links, same as `CreateFeedbackIssueJob`'s issue body. No notification of any kind fires on resolution — this panel is ticket control only. Auth mirrors Solid Errors' credentials-first/ENV-second pattern (`Rails.application.credentials.dig(:admin, :username/:password)` then `ENV["ADMIN_USERNAME"]`/`PASSWORD`) but, unlike Solid Errors, resolves it live per-request in `authenticate_admin` rather than once at boot (so tests can flip `ENV` per example without an app reload) and denies access outright — always `401`, no open fallback — when neither source is configured; this is intentionally stricter than Solid Errors' unset-password-means-open default. See README's "Ticket lifecycle" section.
- Notifications: noticed's install migrations (`db/migrate/*_create_noticed_tables*`, `*_add_notifications_count_to_noticed_event*`) create `noticed_events` (the thing that happened, optional polymorphic `record`) and `noticed_notifications` (one row per recipient, `read_at`/`seen_at`) on the primary DB. Installed noticed is 3.0.0, which keeps the Event/Notification split introduced in v2 (a full rewrite of v1's single-class design) — database persistence is core, not a delivery method — `deliver_by :database` is deprecated and a no-op (`Noticed::Deliverable#deliver_by`); `SomeNotifier.deliver(recipients)` always saves synchronously inside a transaction, then unconditionally enqueues `Noticed::EventJob` (an `ActiveJob::Base` subclass, runs on Solid Queue here) — only declared delivery methods (`:email`, `:action_cable`, etc.) actually run through that job; a notifier with none still enqueues a no-op job. `ApplicationNotifier < Noticed::Event` (`app/notifiers/application_notifier.rb`) is the only app/ notifier code — the template ships zero notifiers. `User` has `has_many :notifications, as: :recipient, dependent: :destroy, class_name: "Noticed::Notification"`. The navbar bell (`app/views/shared/_notification_bell.html.erb`, `app/helpers/notifications_helper.rb`) and `/notifications` (`NotificationsController`, scoped through `Current.user`) render whatever `message` a notifier's `notification_methods` block defines. `TestNotifier` (`test/notifiers/`, required via a `test/test_helper.rb` glob, never used by app code) is the only notifier in the repo — it exercises the full pipeline (deliver → persisted → unread count → mark read) and the `deliver_by :email` opt-in pattern (guarded by `config.if`, backed by `TestNotifierMailer`). See README's "Notifications" section for the create-a-notifier recipe and the email opt-in pattern.
- Log viewer: onlylogs 0.7 mounted at `/onlylogs` (`config/routes.rb`, next to Solid Errors). Production logs broadcast (`ActiveSupport::BroadcastLogger` in `config/environments/production.rb`) to STDOUT (Kamal capture unchanged) AND `storage/logs/production.log`, rotated by Ruby's `Logger` (`5, 100.megabytes` → at most `production.log` + `.0`–`.3`, ~500 MB hard cap on the storage volume). `config/initializers/onlylogs.rb` whitelists exactly that path via `config.log_file_patterns` (the gem auto-permits `.log.N` rotation suffixes and lists them in the viewer; `log/<env>.log` is added outside production so the viewer works locally) and bypasses the gem's built-in basic auth (403-when-unconfigured, ENV-before-credentials, read once at Configuration.new) with its documented custom-auth hook: `config.disable_basic_authentication = true` + `config.parent_controller = "OnlylogsBaseController"`. That controller (`app/controllers/onlylogs_base_controller.rb`) defines `authenticate_onlylogs_user!` mirroring `Admin::FeedbacksController#authenticate_admin`: credentials-first (`onlylogs.basic_auth_user`/`basic_auth_password`), ENV-second (`ONLYLOGS_BASIC_AUTH_USER`/`ONLYLOGS_BASIC_AUTH_PASSWORD` — the gem's native var names, kept on purpose), live per-request, secure_compare, always 401 when unconfigured. **Basic auth covers the HTTP surface only**: the live tail runs over Action Cable and `Onlylogs::LogsChannel` never checks onlylogs credentials — its boundary is the app's cable connection (any signed-in user; the template ships open self-registration) plus whitelist + `SecureFilePath` encryption. The gem's blank-`file_path` fallback streams `default_log_file_path` with NO decryption/whitelist check (`logs_channel.rb:31-34` in onlylogs 0.7.0), so the initializer deliberately sets `config.default_log_file_path = ""` (a never-existing path the channel's text-file check rejects); never point it at a real log — `test/channels/onlylogs_logs_channel_test.rb` guards this. Residual risk: a signed-in user holding a valid encrypted path token (non-expiring, secret_key_base-keyed, normally rendered only behind `/onlylogs` basic auth) can still stream that whitelisted file over the socket. Upstream gap to patch in renuo/onlylogs: no parent_controller-equivalent hook for the channel. Stage 2 (streaming all apps to one central onlylogs server) is deliberately out of scope until the server side is publicly self-hostable — see README's "Log viewer".
- Authorization: pundit as capability only — the template ships zero concrete policies (`Current.user` scoping remains the authorization until an app needs roles/shared resources). `ApplicationController` includes `Pundit::Authorization`, overrides `pundit_user` to `Current.user` (pundit defaults to `current_user`, which this app doesn't define), and `rescue_from Pundit::NotAuthorizedError` redirects back (fallback root) with an alert. `ApplicationPolicy` (`app/policies/`) is the installed generator's default-deny base, comments stripped. No `verify_authorized`/`verify_policy_scoped` anywhere — documented in README's "Authorization" as the opt-in strictness knob. The only policy in the repo is the test-only `PunditTestRecordPolicy` for the test-only `PunditTestRecord` PORO (`test/policies/`, required via a `test/test_helper.rb` glob, never loaded by app code — the TestNotifier pattern; deliberately NOT a policy for a real model, so it can never silently merge with a policy a child app writes, e.g. README's `DocumentPolicy` example), exercised by `test/policies/*_test.rb` and `test/controllers/pundit_wiring_test.rb` (permit, deny → rescue redirect + alert, `policy_scope` filtering, via a test-local controller and `with_routing` — no app routes or controllers touched).
- Deploy: `config/deploy.yml` (placeholders in UPPERCASE; `storage/` volume is mandatory for SQLite + Active Storage).
